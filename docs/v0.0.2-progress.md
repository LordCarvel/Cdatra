## Objetivo da v0.0.2

A v0.0.1 provou a ideia num banco de testes (H2). Na v0.0.2, o Cdatra deve virar uma **ORM/lib de uso real**,
para montar a camada de banco dos meus projetos, com suporte ao **Cloudflare D1**, o banco que mais uso hoje.
Por isso, em decisões de design, vale o que for melhor **a longo prazo** e o padrão de bibliotecas maduras,
mesmo que custe uma tarefa a mais. O Claude explica o custo e o ganho, e eu escolho.

- O Claude atua como **tutor**: explica o conceito antes, eu escrevo o código, ele revisa.
- **Uma tarefa pequena por vez** (um método, um TODO), com conceito e sintaxe só daquela tarefa.

  No `Repository`, a variável que recebe o `SqlQuery` se chama `query`.

## Decisões tomadas

- **`DatabaseAdapter`** com 3 operações: `execute`, `query` (devolve `List<List<Row>>`) e `executeAndReturnGeneratedKey`. A conexão é estado interno de cada adapter.
- Por enquanto, os métodos mantêm `throws SQLException`. Revisar quando chegar o D1 (erros HTTP).
- Um objeto **`SqlQuery`** (SQL + parâmetros) em vez de passar `sql` e `params` separados.
- **`SqlBuilder`** em vez de passar listas soltas entre métodos: texto e parâmetros moram juntos, então a ordem dos `?` não tem como se perder. O `append` recusa `null`; o `appendParameter` aceita `null` (vira NULL no banco).
- **`appendCondition`** (para `WHERE`): `null` vira `IS NULL` / `IS NOT NULL`, sem parâmetro; outros operadores com `null` são recusados.
- **`appendAssignment`** (para `SET`): `null` vira parâmetro. Mesmo `=`, significado diferente do `WHERE`.
- Escrever no `SqlBuilder` **na ordem do SQL** (da esquerda para a direita). No `update`, o `appendCondition` do ID vem depois do `SET`.
- Validar `table` antes de usar `table.getName()`, para manter `IllegalArgumentException` (e não `NullPointerException`) como contrato.
- **`Repository.update`** de uma entidade só com ID: não executa nada, mas recusa ID `null` com `IllegalArgumentException("Update ID value cannot be null")`.
- **`SqlExecutor`** só aceita `SqlQuery`. O caminho inseguro (SQL montado com `String`) não existe mais na lib.
- **`SqlDialect`** responde duas perguntas do `CREATE TABLE`:
  - `String typeName (SqlType type)`: como escrever o tipo naquele banco;
  - `String generatedIdColumn (String columnName, SqlType type)`: a coluna de ID gerado **inteira** (o D1 muda o tipo e a ordem das palavras).
  - O `TypeMapper` (Java → `SqlType`) continua independente do banco, porque também valida valores. O dialeto entra depois dele.
  - No `createTable`: toda coluna gerada é um ID (o `validateTable` garante); ID gerado → `generatedIdColumn`; ID comum → `nome + typeName + " PRIMARY KEY"`; coluna comum → `nome + typeName`.
- **`D1Dialect`** usa `INTEGER PRIMARY KEY AUTOINCREMENT` no ID gerado. O `AUTOINCREMENT` nunca reaproveita IDs apagados,
  o que evita que referências antigas (links, cache, logs) passem a apontar para outro registro. Também é o mesmo comportamento
  do `IDENTITY` do H2 e o padrão de Django, Rails e Prisma. O custo é uma escrita a mais na `sqlite_sequence` a cada `INSERT`.
  - O `generatedIdColumn` usa `typeName(type)`, que devolve `INTEGER` também para `BIGINT`. Um teste trava essa saída,
    porque só a palavra exata `INTEGER` vira apelido do `rowid` (e `BIGINT PRIMARY KEY AUTOINCREMENT` é erro no SQLite).
- `Main.java` (vazio, não rastreado, nos dois PCs) fica: vou usar para um teste manual com o D1 no fim.

Lembretes:

- `?` só substitui **valores**, nunca nomes de tabela/coluna, operadores ou palavras-chave. A validação de identificadores continua essencial.
- Os testes de integração do `Repository` não devem mudar; eles provam que o comportamento foi preservado.

## Pendências e ideias anotadas

- **Grupos com parênteses** no `selectByFilters`: hoje `a OR b AND c` é lido pelo banco como `a OR (b AND c)`, porque o `AND` tem prioridade. Para uso real, a lib vai precisar de grupos. Com o `SqlBuilder` é só `append("(")` ... `append(")")`. Fazer depois do D1.
- Aviso antigo do IntelliJ: `import java.lang.reflect.Field` não usado em `mapping/Container.java`.

## Notas para o D1

- Decisão já tomada: o Java fala com um **Worker próprio** (que tem o binding do D1) por HTTP, e não direto com a API REST da Cloudflare. Assim a aplicação não guarda um token com poder sobre a conta inteira.
- Peças: Worker + protocolo (`{ sql, params }` → linhas + `last_row_id`), `D1DatabaseAdapter` usando `java.net.http.HttpClient` (Java 17, sem dependência), conversão de tipos.
- O D1 não tem `BOOLEAN` (volta 0/1). Números chegam via JSON sem distinção int/long/double. O `ObjectMapper` e o `setGeneratedValue` fazem `field.set` direto, então será preciso decidir onde fica a conversão de tipos.
- O ID gerado vem em `meta.last_row_id`.
- O D1 não tem transações interativas (só `batch`).
- Sem dependências em produção (hoje só JUnit e H2, nos testes): decidir entre um parser JSON mínimo próprio ou uma biblioteca (Jackson, Gson).
