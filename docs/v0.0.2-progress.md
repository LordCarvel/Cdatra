A v0.0.1 provou a ideia num banco de testes (H2). A v0.0.2 transforma o Cdatra numa lib de uso real,
com suporte ao **Cloudflare D1**, sem quebrar o que já funcionava no H2.

## Decisões

### Arquitetura

- **`DatabaseAdapter`** com quatro operações: `execute`, `query` (devolve `List<List<Row>>`), `executeAndReturnGeneratedKey` e `dialect`.
  A conexão é estado interno de cada adapter.
- **Quem escolhe o dialeto é o adapter.** Escolher o adapter já escolhe o banco, e não dá para combinar o adapter do D1
  com o dialeto do H2 (modelo do Exposed e do jOOQ). O `JdbcDatabaseAdapter` serve a vários bancos e recebe o dialeto no construtor;
  o construtor só com `Connection` usa H2, compatível com a v0.0.1.
- No `Repository`, o `SqlGenerator` é criado no construtor, depois da validação do adapter. Um `dialect()` `null` é recusado pelo `SqlGenerator`.

### SQL parametrizado

- **`SqlQuery`** (SQL + parâmetros) em vez de `sql` e `params` separados.
- **`SqlBuilder`**: texto e parâmetros moram juntos, então a ordem dos `?` não se perde. É escrito na ordem do SQL, da esquerda para a direita.
  O `append` recusa `null`; o `appendParameter` aceita `null` (vira NULL no banco).
- **`appendCondition`** (`WHERE`): `null` vira `IS NULL`/`IS NOT NULL`, sem parâmetro; outros operadores com `null` são recusados.
- **`appendAssignment`** (`SET`): `null` vira parâmetro. Mesmo `=`, significado diferente do `WHERE`.
- **`SqlExecutor`** só aceita `SqlQuery`. O caminho com SQL montado em `String` não existe mais.
- `?` só substitui **valores**, nunca nomes de tabela ou coluna, operadores ou palavras-chave. A validação de identificadores continua necessária.
- `table` é validada antes de `table.getName()`, para manter `IllegalArgumentException` (e não `NullPointerException`) como contrato.
- **`Repository.update`** de uma entidade só com ID não executa nada, mas recusa ID `null` com `IllegalArgumentException("Update ID value cannot be null")`.

### Dialetos

- **`SqlDialect`** responde duas perguntas do `CREATE TABLE`:
  - `String typeName (SqlType type)`: como escrever o tipo naquele banco;
  - `String generatedIdColumn (String columnName, SqlType type)`: a coluna de ID gerado inteira, porque o D1 muda o tipo e a ordem das palavras.
- O `TypeMapper` (Java → `SqlType`) continua independente do banco, porque também valida valores. O dialeto entra depois dele.
- **`D1Dialect`**: `BIGINT`/`BOOLEAN` → `INTEGER`, `VARCHAR` → `TEXT`, `DOUBLE` → `REAL`, e ID gerado como `INTEGER PRIMARY KEY AUTOINCREMENT`.
  O `AUTOINCREMENT` nunca reaproveita IDs apagados, então referências antigas (links, cache, logs) não passam a apontar para outro registro.
  É o comportamento do `IDENTITY` do H2 e o padrão de Django, Rails e Prisma. O custo é uma escrita a mais na `sqlite_sequence` a cada `INSERT`.
  Só a palavra exata `INTEGER` vira apelido do `rowid` (`BIGINT PRIMARY KEY AUTOINCREMENT` é erro no SQLite); um teste trava essa saída.

### Erros e conversão de tipos

- **`CdatraException`** (`RuntimeException`) é o único erro da API pública, para qualquer banco, com o erro original como causa
  (padrão de Hibernate, jOOQ e Spring). O `JdbcDatabaseAdapter` traduz `SQLException`, e o `ObjectMapper` e o `ValueAnalysis` traduzem as exceções de reflexão.
  O `Repository` não declara nenhum `throws`. O `SqlExecutor` continua com `SQLException`, porque é a parte que fala JDBC.
- **`ValueConverter`** (pacote `mapping`) converte pelo tipo do campo, para todos os bancos: `Long` → `int`/`boolean`/`double`.
  Fica fora do adapter, que não sabe qual entidade pediu os dados. Número que não cabe (`int` estourado, `2` em `boolean`) é recusado, nunca cortado.
  `Long` em `double` é necessário porque o JavaScript escreve `2.0` como `2`.
- A ida para o D1 (`boolean` → `1`/`0`, recusa de `long` acima de 2⁵³ − 1) fica no `D1DatabaseAdapter`, porque só depende do valor.

### Consultas

- **`LIKE`:** quem chama escreve os curingas (`findBy("name", "Car%", Operator.LIKE)`), como no SQL. Valor que não é texto é recusado antes de ir ao banco.
  Diferenças entre os bancos, conferidas em 02/11 e mantidas de propósito: no D1, o `LIKE` ignora maiúsculas e minúsculas só nas letras
  sem acento (`car%` acha `Carvel`; `JOÃO` não acha `João`), e no H2 sempre diferencia. No D1, o padrão aceita no máximo 50 bytes; acima disso vem `SQL_ERROR`.
- **Grupos no `selectByFilters`:** sem parênteses, `a OR b AND c` é lido como `a OR (b AND c)`. Um `QueryFilter` pode guardar um grupo
  no lugar da condição: `QueryFilter.group(lista, operador)`. É um método `static`, e não um segundo construtor, porque
  `new QueryFilter(null, LogicalOperator.AND)` ficaria ambíguo. Grupo vazio é recusado, e um grupo pode ficar dentro de outro.

### JSON próprio (pacote `internal.json`)

Parser próprio, sem dependência em produção: uma lib não deve impor dependências (conflitos de versão, como com o Jackson),
o escopo é pequeno e os dois lados são nossos. O pacote `internal` não é API pública, então trocar por uma biblioteca depois não quebra ninguém.

- Tipos: objeto → `Map<String, Object>` (`LinkedHashMap`), array → `List<Object>`, texto → `String`,
  `1` → `Long`, `1.5` e `2e3` → `Double`, `true`/`false` → `Boolean`, `null` → `null`.
- **`JsonWriter`:** escapa `"`, `\` e caracteres de controle; chave de mapa precisa ser `String`; `NaN` e `Infinity` são recusados.
- **`JsonReader`:** um objeto por texto, e texto sobrando depois do valor é recusado (*fail fast*), para não esconder uma resposta quebrada do Worker.
  - Espaço em branco só é `' '`, `\t`, `\n` e `\r`; dígito só é `0`–`9` (`Character.isWhitespace` e `isDigit` aceitam mais do que o JSON permite).
  - Números: recusa `1.`, `-.5` e zero à esquerda; inteiro fora do `Long` é recusado em vez de virar `Double` arredondado; `1e400` é recusado, `1e-400` vira `0.0`.
  - Textos: escapes simples e `\uXXXX`; caracteres de controle crus são recusados; DEL (127) é permitido. Metade de um emoji sozinha é aceita, porque o `JSON.stringify` pode produzi-la.
  - Listas e mapas por recursão; vírgula sobrando é recusada; chave repetida fica com o último valor, como no `JSON.parse`.

## D1 e Worker

O Java fala com um **Worker próprio**, que tem o binding do D1, por HTTP, e não direto com a API REST da Cloudflare.
Assim a aplicação não guarda um token com poder sobre a conta inteira.

- **`D1DatabaseAdapter`** (pacote `d1`): `java.net.http.HttpClient` do JDK, timeout de 30 s, `Authorization: Bearer`.
  Falha de rede e `ok: false` viram `CdatraException`; corpo que não é JSON é informado com o status HTTP.
  O ID gerado vem de `meta.last_row_id`. Os testes usam um Worker falso com o `com.sun.net.httpserver.HttpServer` do JDK.
- **Worker** (`worker/`): JavaScript puro, sem build.
  - Sem `CDATRA_SECRET` configurado, tudo é recusado com 500 `INTERNAL` (erro de configuração do servidor, não de quem chamou).
  - O segredo é comparado pelo hash SHA-256 com `crypto.subtle.timingSafeEqual`, e não com `===`, que revelaria o segredo pelo tempo de resposta.
    A ordem é 500, 401 e só então a rota, para quem não tem o segredo não descobrir quais rotas existem.
  - A rota é conferida antes do corpo, para um endereço errado dar 404, e não 400.
  - `/v1/query` usa `raw({ columnNames: true })`; `/v1/execute` usa `run()` e devolve só `meta.last_row_id`. Erro do D1 vira 400 `SQL_ERROR`.
  - Testes com `node:test`, banco falso e um substituto do `timingSafeEqual`, que não existe no Node.
- **Conferência de ponta a ponta** (02/11): 17 verificações com o adapter e o `Repository` de verdade, primeiro com `wrangler dev`
  (banco local) e depois com o D1 real numa conta de testes: `createTable`, `save` com ID gerado, `findAll`, `findById`, `findBy`,
  `update` e `delete`; acento e símbolo no texto; `boolean`, `2.0` em `double` e `Integer` nulo; segredo errado dá `UNAUTHORIZED`;
  SQL sem parâmetros (`bind()` vazio); `long` de 2⁵³ − 1 aceito e 2⁵³ recusado no Java.
- **Configuração real fora do git**, porque o repositório é público: `worker/.dev.vars` (segredo local, um por PC),
  `worker/.prod.vars` (segredo de produção) e `worker/wrangler.prod.toml` (`account_id` e `database_id` reais).
  O `wrangler.toml` rastreado fica com zeros. Publicar: `npx.cmd wrangler deploy --config wrangler.prod.toml`;
  enviar o segredo: `Get-Content .prod.vars | npx.cmd wrangler secret put CDATRA_SECRET`. Conferir a conta com `npx wrangler whoami` antes.

## Protocolo v1 (Java ↔ Worker)

- Ida: `POST /v1/query` (leituras) ou `POST /v1/execute` (escritas), header `Authorization: Bearer <segredo>`, corpo `{ "sql": "...", "params": [...] }`.
- Sucesso (HTTP 200): `{ "ok": true, "result": { "columns": [...], "rows": [[...]], "meta": { "last_row_id": n } } }`.
  `/v1/query` preenche `columns` e `rows`; `/v1/execute` preenche `meta.last_row_id`, com as listas vazias.
  `columns` + `rows`, e não um objeto por linha, mantém a ordem e não perde colunas de mesmo nome num `JOIN`.
- **Por que duas rotas:** no D1, `raw({ columnNames: true })` traz colunas e linhas sem `meta`, e `run()` traz `meta` com objetos por linha.
  Nenhum método entrega tudo, e rodar os dois executaria o comando duas vezes. Adivinhar pelo início do SQL quebraria com `RETURNING`, `WITH` e comentários.
- Erro: `{ "ok": false, "error": { "code": "...", "message": "..." } }`, com `UNAUTHORIZED` (401), `BAD_REQUEST` (400),
  `NOT_FOUND` (404), `SQL_ERROR` (400) e `INTERNAL` (500).
- Valores: `null`, texto e número; `boolean` vai como `1`/`0`. `long` fora de ±(2⁵³ − 1) é recusado no Java, porque o JavaScript perderia a precisão.
- O Java ignora campos que não conhece, para aceitar respostas de Workers mais novos.

## Levado para a v0.0.3

  com o índice do comando que falhou, `meta.changes` no `update`/`delete` e as métricas `rows_read`/`rows_written`/`duration`.

- Descobrir o dialeto por `connection.getMetaData().getDatabaseProductName()`.
