## Decisões tomadas

- **`DatabaseAdapter`** com 3 operações: `execute`, `query` (devolve `List<List<Row>>`) e `executeAndReturnGeneratedKey`. A conexão é estado interno de cada adapter.
- Por enquanto, os métodos mantêm `throws SQLException`. Revisar quando chegar o D1 (erros HTTP).
- **Opção C**: um objeto `SqlQuery` em vez de passar `sql` e `params` separados.
- **Andaime temporário**: os métodos de `String` do `SqlExecutor` foram mantidos (veja a limpeza pendente).

## Plano de conversão do SqlGenerator

Converter um método por vez, sempre em 3 movimentos:
`SqlGenerator` devolve `SqlQuery` → ajustar o assert do teste → `Repository` tira o embrulho.

1. **Sem valores:** `selectAll` ⏳, depois `createTable`
2. **Valores próprios:** `insert`
3. **Usam `buildCondition`:** `selectById`, `selectBy`, `selectByConditions`, `selectByFilters`, `update`, `delete` (exige uma decisão de design; discutir antes)

Lembretes:

- `?` só substitui **valores**, nunca nomes de tabela/coluna, operadores ou palavras-chave. A validação por regex de identificadores continua essencial.
- Uma condição com `null` continua `IS NULL` / `IS NOT NULL`, sem parâmetro. No `INSERT`/`SET`, `null` pode ser parâmetro.
- Os testes de integração do `Repository` não devem mudar; eles provam que o comportamento foi preservado.

## Notas para o D1 (futuro)

- No SQLite, só `INTEGER PRIMARY KEY` vira autoincremento; `BIGINT PRIMARY KEY` não. Isso é um caso para o dialect.
- O D1 não tem `BOOLEAN` (volta 0/1). Números chegam via JSON sem distinção int/long/double. O `ObjectMapper` e o `setGeneratedValue` fazem `field.set` direto, então será preciso decidir onde fica a conversão de tipos.
- O ID gerado vem em `meta.last_row_id`.
- O D1 não tem transações interativas (só `batch`).
- Sem dependências: decidir entre um parser JSON mínimo próprio ou uma biblioteca.
