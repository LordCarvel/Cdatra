## Objetivo da v0.0.2

A v0.0.1 provou a ideia num banco de testes (H2). Na v0.0.2, o Cdatra deve virar uma **ORM/lib de uso real**,
para montar a camada de banco dos meus projetos, com suporte ao **Cloudflare D1**, o banco que mais uso hoje.
Por isso, em decisões de design, vale o que for melhor **a longo prazo** e o padrão de bibliotecas maduras,
mesmo que custe uma tarefa a mais. O Claude explica o custo e o ganho, e eu escolho.

**Roteiro:** v0.0.2 = suporte ao D1 (objetivo principal). v0.0.3, logo depois = ORM mais completa (operações mais ricas).

**Princípio de design:** ao pensar em opções, escolher a forma que as próximas versões possam **estender sem quebrar**
(estrutura estável, espaço para campos, códigos e rotas novos), mas implementar **só o que a versão atual usa**.
Nada de construir recursos "para depois". Em cada opção, dizer o que entra agora, o que fica para depois
e por que a forma escolhida deixa a parte adiada entrar sem reescrever.

## Forma de trabalho

- O Claude atua como **tutor**: explica o conceito antes, eu escrevo o código, ele revisa.
- **Uma tarefa pequena por vez** (um método, um TODO), com conceito e sintaxe só daquela tarefa.
  Quando a tarefa tiver vários passos, dividir em partes (3a, 3b...).
  **Eu monto o código:** o Claude descreve o que fazer e mostra só a sintaxe nova, sem entregar o método ou arquivo quase pronto com lacunas.
  Cada explicação começa pelo motivo prático da tarefa. Toda sintaxe nova vem no próprio passo em que é usada, com o que cada pedaço significa. Todo método novo vem com a assinatura explicada: o que recebe, o que devolve e por quê. Números de linha valem para o arquivo atual: conferir antes de citar. Rapidez nunca justifica cortar explicação.
  Código mecânico, sem conceito que eu vá reutilizar, fica com o Claude, mesmo que não seja uma cadeia de tipos.
  Explicações em texto corrido, com analogias e o caminho que o código percorre ao rodar, comparando com o que eu já escrevi. Tabelas podem apoiar, mas não substituem a explicação.
  **Mensagens curtas:** cada mensagem começa pela ação exata (onde escrever e o quê), com uma ação só e pouco texto depois. A explicação não some: é dividida em mensagens pequenas, e o Claude aprofunda quando eu pedir.

## Decisões tomadas

- **`DatabaseAdapter`** com 3 operações: `execute`, `query` (devolve `List<List<Row>>`) e `executeAndReturnGeneratedKey`. A conexão é estado interno de cada adapter.
- **`CdatraException`** (`RuntimeException`) será o único erro da API pública, para qualquer banco; é o padrão de Hibernate, jOOQ e Spring. O erro original fica como causa.
  Em três tarefas: (1) criar a classe ✅; (2) o `JdbcDatabaseAdapter` traduz `SQLException`, e os `throws` saem do `DatabaseAdapter` e do `Repository` ✅; (3) traduzir também as exceções de reflexão ✅.
  O `SqlExecutor` continua com `SQLException`: é a parte que fala JDBC. Subclasses (como `CONSTRAINT`) ficam para a v0.0.3, sem quebrar quem faz `catch (CdatraException e)`.
- Um objeto **`SqlQuery`** (SQL + parâmetros) em vez de passar `sql` e `params` separados.
- **`SqlBuilder`** em vez de passar listas soltas entre métodos: texto e parâmetros moram juntos, então a ordem dos `?` não tem como se perder. O `append` recusa `null`; o `appendParameter` aceita `null` (vira NULL no banco).
- **`appendCondition`** (para `WHERE`): `null` vira `IS NULL` / `IS NOT NULL`, sem parâmetro; outros operadores com `null` são recusados.
- **`appendAssignment`** (para `SET`): `null` vira parâmetro. Mesmo `=`, significado diferente do `WHERE`.
- Escrever no `SqlBuilder` **na ordem do SQL** (da esquerda para a direita). No `update`, o `appendCondition` do ID vem depois do `SET`.
- Validar `table` antes de usar `table.getName()`, para manter `IllegalArgumentException` (e não `NullPointerException`) como contrato.
- **`Repository.update`** de uma entidade só com ID: não executa nada, mas recusa ID `null` com `IllegalArgumentException("Update ID value cannot be null")`.
- **`SqlExecutor`** só aceita `SqlQuery`. O caminho inseguro (SQL montado com `String`) não existe mais na lib.
- **`SqlDialect`** responde duas perguntas do `CREATE TABLE`:
  - `String typeName (SqlType type)`: como escrever o tipo naquele banco;
  - `String generatedIdColumn (String columnName, SqlType type)`: a coluna de ID gerado **inteira** (o D1 muda o tipo e a ordem das palavras).
  - O `TypeMapper` (Java → `SqlType`) continua independente do banco, porque também valida valores. O dialeto entra depois dele.
  - No `createTable`: toda coluna gerada é um ID (o `validateTable` garante); ID gerado → `generatedIdColumn`; ID comum → `nome + typeName + " PRIMARY KEY"`; coluna comum → `nome + typeName`.
- **`D1Dialect`** usa `INTEGER PRIMARY KEY AUTOINCREMENT` no ID gerado. O `AUTOINCREMENT` nunca reaproveita IDs apagados,
  o que evita que referências antigas (links, cache, logs) passem a apontar para outro registro. Também é o mesmo comportamento
  do `IDENTITY` do H2 e o padrão de Django, Rails e Prisma. O custo é uma escrita a mais na `sqlite_sequence` a cada `INSERT`.
  - O `generatedIdColumn` usa `typeName(type)`, que devolve `INTEGER` também para `BIGINT`. Um teste trava essa saída,
    porque só a palavra exata `INTEGER` vira apelido do `rowid` (e `BIGINT PRIMARY KEY AUTOINCREMENT` é erro no SQLite).
- **Quem escolhe o dialeto é o adapter** (`SqlDialect dialect ()` no `DatabaseAdapter`, sem `throws`). Escolher o adapter já escolhe o banco,
  e não dá para combinar o adapter do D1 com o dialeto do H2. É o modelo do Exposed e do jOOQ.
  - O `JdbcDatabaseAdapter` serve para vários bancos, então recebe o dialeto no construtor. O construtor só com `Connection` usa H2 (compatível com a v0.0.1).
    Ideia para depois: descobrir o banco por `connection.getMetaData().getDatabaseProductName()`.
  - No `Repository`, o `sqlGenerator` é criado no construtor, **depois** da validação do adapter. Um `dialect()` `null` é recusado pelo `SqlGenerator`.
- **`ValueConverter`** (pacote `mapping`) converte pelo tipo do campo, para todos os bancos: `Long` → `int`/`boolean`/`double`. O resto passa sem mudança, então o H2 não é afetado.
  Fica fora do adapter porque ele não sabe qual entidade pediu os dados. Número que não cabe (`int` estourado, `2` em `boolean`) é recusado, nunca cortado. `Long` em `double` é necessário: o JavaScript escreve `2.0` como `2`.
  Tipos novos (datas, `BigDecimal`, enums) entram como mais um `if`. A ida (`boolean` → `1`/`0`, recusa de `long` acima de 2⁵³) fica no `D1DatabaseAdapter`, porque só depende do valor.
- **`LIKE`:** quem chama escreve os curingas (`findBy("name", "Car%", Operator.LIKE)`), como no SQL. Atalhos como `CONTAINS` podem entrar depois como novos valores do `enum`.
  Diferenças entre os bancos, conferidas em 02/11 e mantidas de propósito, porque escondê-las exigiria reescrever o `LIKE` de cada um: no D1, ele ignora maiúsculas e minúsculas só nas letras sem acento (`car%` acha `Carvel`; `JOÃO` não acha `João`), e no H2 sempre diferencia. No D1, o padrão aceita no máximo 50 bytes; acima disso vem `SQL_ERROR`.
- **Grupos no `selectByFilters`:** sem parênteses, `a OR b AND c` é lido como `a OR (b AND c)`. Um `QueryFilter` pode guardar um grupo no lugar da condição: `QueryFilter.group(lista, operador)`. É um método `static`, e não um segundo construtor, porque `new QueryFilter(null, LogicalOperator.AND)` ficaria ambíguo. O `new QueryFilter(...)` de sempre não mudou. Grupo vazio é recusado, e um grupo pode ficar dentro de outro.
- `Main.java` (vazio, não rastreado, nos dois PCs) fica: vou usar para um teste manual com o D1 no fim.

Lembretes:

- `?` só substitui **valores**, nunca nomes de tabela/coluna, operadores ou palavras-chave. A validação de identificadores continua essencial.
- Os testes de integração do `Repository` não devem mudar; eles provam que o comportamento foi preservado.

### JSON próprio (pacote `internal.json`)

Decisão: parser próprio, sem dependência em produção. Uma lib não deve impor dependências (conflitos de versão, como com o Jackson);
o escopo é pequeno e nós controlamos os dois lados. O pacote `internal` não é API pública: trocar por uma biblioteca depois não quebra ninguém.

Tipos: objeto → `Map<String, Object>` (`LinkedHashMap`), array → `List<Object>`, texto → `String`,
`1` → `Long`, `1.5` → `Double`, `true`/`false` → `Boolean`, `null` → `null`.

- ✅ **`JsonWriter`** (J1–J4): `write` público + `writeValue` privado num único `StringBuilder`; texto com escape
  (`"` → `\"`, `\` → `\\`, controle < 32 → `\u00XX`); lista e mapa por recursão; chave de mapa precisa ser `String`.
- ✅ **J5:** `NaN` e `Infinity` não existem em JSON e são recusados com `IllegalArgumentException`. O teste vale só para `Double`/`Float`:
  um `BigInteger` enorme vira `Infinity` no `doubleValue()`, mas é um número válido.
- ✅ **`JsonReader`, R1:** um objeto por texto (`new JsonReader(texto).read()`), com `text` e `position` como campos.
  O `startsWith` compara à frente sem mover a posição. Valor só é aceito **exatamente na posição atual** (não é uma busca),
  e texto sobrando depois do valor é recusado (*fail fast*): ignorar esconderia uma resposta quebrada do Worker.
- ✅ **`JsonReader`, R2:** `skipWhitespace` antes e depois do `readValue`. Só `' '`, `\t`, `\n` e `\r` contam como espaço;
  o `Character.isWhitespace` aceita mais do que o JSON permite. No `while`, a posição é conferida antes do `charAt` (com `&&`).
- ✅ **`JsonReader`, R3a:** `readNumber` guarda o início em `start`, anda com `position` pelos dígitos, recorta com `substring` e converte com `Long.parseLong`.
  O `start` nunca muda, e o número pode começar em qualquer posição. O `Character.isDigit` não serve: aceita dígitos de outros alfabetos.
- ✅ **`JsonReader`, R3b:** `isDecimal` guarda se apareceu ponto ou expoente; `skipDigits` anda pelos dígitos. Número com ponto ou expoente vira `Double` (mesmo `2e3`), o resto vira `Long`.
- ✅ **`JsonReader`, R3c1:** `requireDigits` compara a posição antes e depois do `skipDigits` e recusa com a posição se o dedo não andou. Sem isso, o `parseDouble` aceitaria `1.` e `-.5`.
- ✅ **`JsonReader`, R3c2:** zero seguido de dígito é recusado, olhando `position + 1` sem mover o dedo. A verificação vem depois do `-`; no expoente, zeros são permitidos (`1e05`).
- ✅ **`JsonReader`, R3c3:** inteiro fora do `Long` é recusado, e não vira `Double`, que o arredondaria sem aviso. O `parseDouble` devolve `Infinity` sem erro para `1e400`, então o resultado é conferido.
  Os erros apontam `start`, o início do número. `1e-400` continua aceito e vira `0.0`: é arredondamento, não um valor falso.
- ✅ **`JsonReader`, R4a:** `readString` copia caractere por caractere para um `StringBuilder` até a aspa de fechamento. O `return` fica dentro do `while`: se o laço termina sozinho, o texto não fechou, e o erro aponta `start`.
  `substring` não serviria, porque com escapes o resultado deixa de ser um pedaço do original (`\n` são 2 caracteres no JSON e 1 no resultado).
- ✅ **`JsonReader`, R4b:** a barra invertida avisa que o próximo caractere tem outro significado. O `readString` pula a barra, confere se o texto continua, traduz com o `unescape` e usa `continue` para não guardar a barra.
  Depois de avançar o `position`, é preciso ler de novo com `text.charAt(position)`: a variável `c` ainda guarda a barra. O `\u` ainda dá `Invalid escape`.
- ✅ **`JsonReader`, caracteres de controle:** códigos abaixo de 32 precisam vir escapados, então o `readString` recusa os crus com `isControl`, logo antes do último `append`. O erro aponta o caractere (`position`), não o início do texto.
  O escape nunca chega nessa verificação, porque sai antes pelo `continue`. Barra seguida de controle cru dá `Invalid escape`. O DEL (127) é permitido pelo JSON.
- ✅ **`JsonReader`, R4c:** `readUnicodeEscape` junta 4 dígitos com `value = value * 16 + hexValue(...)` e converte com `(char) value`. O Claude escreveu esta parte: é mecânica e não se repete no projeto.
  O `hexValue` é feito à mão porque o `Character.digit` aceita dígitos de outros alfabetos. Um emoji vem como dois escapes, que formam dois `char` sem código especial. Metade de um emoji sozinha é aceita, porque o `JSON.stringify` pode produzi-la a partir do que está no banco.
- ✅ **`JsonReader`, R5a:** `readList` lê `[]` e `[ ]`. O `startsWith("[", position)` precisa do `position`: sem ele, olha o começo do texto inteiro, e não o ponto onde o leitor está. `[1]` ainda dá `Unterminated list`.
- ✅ **`JsonReader`, R5b1:** o `readList` chama o `readValue`, que pode chamar o `readList` de novo (recursão). Funciona porque o `position` é compartilhado: cada chamada continua de onde a anterior parou. Antes do `readValue`, confere se o texto acabou, para `[` dar `Unterminated list`.
- ✅ **`JsonReader`, R5b2:** o `readList` repete um ciclo dentro de um `while`: ler um valor e olhar o que vem depois. `]` devolve, `,` continua, fim do texto usa `break` para cair no `Unterminated list`, e qualquer outra coisa dá `Expected ',' or ']'`. Vírgula sobrando (`[1,]`) é recusada, porque o `readValue` encontra o `]`.
- ✅ **`JsonReader`, R6a:** `readMap` lê `{}` e `{ }`, na mesma forma do `readList`. `LinkedHashMap` mantém a ordem de chegada das chaves. `{"a": 1}` ainda dá `Unterminated map`.
  Imports explícitos: o IntelliJ pode trocar por `import java.util.*` (ajuste em Settings → Editor → Code Style → Java → Imports).
- ✅ **`JsonReader`, R6b:** a chave precisa começar com aspas (`Expected a string key`) e é lida pelo `readString`. O `:` é conferido com `||`: se o texto acabou, o `charAt` nem roda. O valor vem do `readValue`, então mapas e listas podem ficar um dentro do outro.
- ✅ **`JsonReader`, R6c:** o `readMap` usa o mesmo ciclo do `readList`. Vírgula sobrando dá `Expected a string key`. Chave repetida fica com o último valor, como no `JSON.parse`. Testes conferem as respostas de sucesso e de erro do Worker e a ida e volta com o `JsonWriter`.

## Protocolo v1 (Java ↔ Worker), formato da v0.0.2

Mesma estrutura do formato completo; a v0.0.3 só acrescenta rotas, campos e códigos (ver pendências).

- Ida: `POST /v1/query` (leituras) ou `POST /v1/execute` (escritas), header `Authorization: Bearer <segredo>`, corpo `{ "sql": "...", "params": [...] }`.
- Sucesso (HTTP 200): `{ "ok": true, "result": { "columns": [...], "rows": [[...]], "meta": { "last_row_id": n } } }`.
  `/v1/query` preenche `columns` e `rows`; `/v1/execute` preenche `meta.last_row_id`, com as listas vazias.
  `columns` + `rows` (e não um objeto por linha): mantém a ordem e não perde colunas de mesmo nome num `JOIN`.
  **Por que duas rotas:** no D1, `raw({ columnNames: true })` traz colunas e linhas sem `meta`, e `run()` traz `meta` com objetos por linha. Nenhum método entrega tudo, e rodar os dois executaria o comando duas vezes. Adivinhar pelo início do SQL quebraria com `RETURNING`, `WITH` e comentários.
- Erro: `{ "ok": false, "error": { "code": "...", "message": "..." } }`, com `UNAUTHORIZED` (401), `BAD_REQUEST` (400),
  `NOT_FOUND` (404), `SQL_ERROR` (400) e `INTERNAL` (500).
- Valores: `null`, texto, número; boolean vai como `1`/`0` (o Java converte antes de enviar).
- `long` fora de ±2⁵³ é recusado no Java com erro claro: o Worker é JavaScript e perderia a precisão (conferido com o banco local e com o D1 real).
- O Java ignora campos que não conhece, para aceitar respostas de Workers mais novos.

## Notas para o D1

- Decisão já tomada: o Java fala com um **Worker próprio** (que tem o binding do D1) por HTTP, e não direto com a API REST da Cloudflare. Assim a aplicação não guarda um token com poder sobre a conta inteira.
- Peças: Worker + protocolo (`{ sql, params }` → linhas + `last_row_id`), `D1DatabaseAdapter` usando `java.net.http.HttpClient` (Java 17, sem dependência), conversão de tipos.
- O D1 não tem `BOOLEAN` (volta 0/1). Números chegam via JSON sem distinção int/long/double. O `ObjectMapper` e o `setGeneratedValue` fazem `field.set` direto, então será preciso decidir onde fica a conversão de tipos.
- O ID gerado vem em `meta.last_row_id`.
- O D1 não tem transações interativas (só `batch`).
- Sem dependências em produção (hoje só JUnit e H2, nos testes): JSON próprio, já decidido.
