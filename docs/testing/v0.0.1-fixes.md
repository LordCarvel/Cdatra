# Correções e validação final — Cdatra v0.0.1

Data: 08/10/2026. Commit das correções: `d3e5454`.

Os 11 grupos de problemas da auditoria anterior foram corrigidos nos métodos
existentes. Os 25 casos que falhavam agora passam. A bateria foi ampliada para
**224 casos**, todos passando, sem testes ignorados ou excluídos.

## O que mudou

| Grupo | Correção |
| --- | --- |
| D01 — UPDATE com chave textual | UPDATE usa buildCondition, que escapa os apóstrofos da chave. O teste confirma a atualização da chave maliciosa como dado e a preservação do outro registro. |
| D02 — validação do UPDATE | Rejeita ID/Row/nome nulos, colunas desconhecidas, duplicadas, tipos incompatíveis e alteração de colunas de ID. |
| D03 — DELETE com identificador malformado | Valida metadados e coluna antes de gerar SQL. O teste exige rejeição e confirma que as duas linhas continuam no banco. |
| D04 — entidade com apenas ID gerado | INSERT usa DEFAULT VALUES. UPDATE sem campos mutáveis valida o ID e não emite SQL vazio. O teste completa save, busca, update e delete. |
| D05 — ID herdado | Analysis, ValueAnalysis e ObjectMapper percorrem a hierarquia. O teste agora verifica o CRUD completo da entidade com ID herdado. |
| D06 — campos static | Campos estáticos e sintéticos são ignorados na análise, extração de valores e mapeamento. O campo compartilhado não é sobrescrito. |
| D07 — labels duplicados | O mapper rejeita labels repetidos sem diferenciar maiúsculas/minúsculas antes de instanciar ou preencher a entidade. |
| D08 — anotação incompleta | GeneratedValue sem Column é rejeitado. Geração de ID exige int/Integer ou long/Long e associação com Id. |
| D09 — executor de chave gerada | Reutiliza validate para conexão e SQL, como execute/query. |
| D10 — metadados inconsistentes | Todos os caminhos de geração verificam nomes, colunas, tipos e flags. Nomes com expressões SQL e tabelas sem colunas são rejeitados. |
| D11 — números não finitos | NaN e infinidades são rejeitados em INSERT, UPDATE, DELETE e consultas, sem produzir SQL com esses valores. |

Também foram corrigidos estes pontos relacionados:

- Repository rejeita tipo ou conexão nulos no construtor.
- O schema rejeita mais de uma coluna de ID e combinações inválidas de geração.
- INSERT rejeita valor nulo explícito para coluna de ID.
- Consultas e UPDATE verificam compatibilidade entre os tipos SQL declarados e os
  valores recebidos. Não foi criada conversão automática de tipos.
- O cast de resultados usa Class.cast, removendo o aviso de cast genérico inseguro.
- Main usa try-with-resources para fechar a conexão inclusive quando ocorrer erro.

Não foram criados métodos, construtores, classes ou funcionalidades de API novos.
As declarações explícitas de produção foram comparadas com a revisão anterior;
as assinaturas permanecem iguais. Os testes foram ampliados dentro dos métodos e
providers já existentes, acrescentando 18 entradas parametrizadas.

O teste antigo de DELETE executava o SQL malformado para demonstrar a perda de
dados. Agora exige IllegalArgumentException antes da execução e verifica que as
linhas foram preservadas. Essa mudança adapta a reprodução ao contrato corrigido.

## Escopo validado para publicação

A compilação e a bateria não apresentam erros no ambiente avaliado: Java 17,
JUnit 5.11.4, Maven 3.9.14 e H2 2.5.250 em memória. Foram mantidos os testes de
CRUD, transações, duas conexões, texto com apóstrofos/Unicode, filtros e repetição
com 500 registros. Os problemas reproduzidos na avaliação anterior estão resolvidos.

Os limites continuam explícitos:

- Identificadores devem seguir `[A-Za-z_][A-Za-z0-9_]*`; nomes reservados pelo banco
  precisam ser evitados. Não foi adicionada uma API de quoting ou nomes qualificados.
- Valores precisam corresponder ao tipo SQL da coluna. Int/Integer e long/Long
  pertencem a tipos SQL diferentes; não há conversão geral entre eles.
- O gerador ainda retorna SQL textual. Os cenários de injeção identificados foram
  corrigidos por validação de identificadores, conferência de tipos e escape de
  apóstrofos, sem mudar a API para uma lista de parâmetros JDBC.
- Outros bancos, persistência em disco, falhas de rede e acesso concorrente por
  threads não foram certificados. Testes verdes não garantem ausência de todo bug.

O `pom.xml` permanece em `1.0-SNAPSHOT`. Esta revisão prepara o código no escopo
testado; não cria tag de release nem publica um pacote em um repositório Maven.
