# Relatório de testes — Cdatra v0.0.1

> Histórico da revisão `80036c9`. Os problemas abaixo foram corrigidos depois
> desta avaliação. Consulte o [resultado atual](v0.0.1-fixes.md), com 224 testes
> passando e nenhuma exclusão de testes de defeitos.

Data: 08/10/2026, horário de São Paulo.

O CRUD funciona nos fluxos regulares testados, incluindo IDs gerados, buscas,
filtros, atualização, exclusão e transações controladas pelo chamador. A avaliação
completa também reproduziu falhas de integridade dos dados. A versão ainda precisa
de correções antes de ser usada com entradas externas, principalmente no UPDATE
com chave textual e no DELETE feito diretamente pelo gerador de SQL.

Esta revisão alterou apenas testes, configuração de testes/cobertura e documentação.
Nenhum arquivo de `src/main/java` foi modificado. Os defeitos continuam no código
de produção e possuem testes que falham para demonstrá-los.

## Uso completo do sistema

O teste de ciclo completo cria a tabela de uma entidade, confirma o banco vazio,
salva dois registros, verifica as chaves atribuídas, busca por ID, mapeia todos os
valores, atualiza um registro e confirma que o outro ficou intacto. Depois exclui
o registro, verifica a ausência e repete a exclusão sem afetar o restante.

Também foram executados estes cenários:

- Texto vazio, espaços, apóstrofos, acentos, japonês, emoji, quebra de linha e tab.
- Texto como `'; DROP TABLE records; --`, preservado como dado nos fluxos regulares
  de INSERT, busca simples, condições, filtros e atualização de campo textual.
- Texto de 10.000 caracteres, `Long.MIN_VALUE`, `Long.MAX_VALUE`, limites de Integer
  e `Double.MAX_VALUE`, além de números negativos e campos objeto nulos.
- IDs Integer e Long gerados, IDs manuais, IDs String sem apóstrofo e a entidade
  `User` real do projeto. A chave fornecida no User é substituída pelo ID gerado.
- Violação de chave primária, tabela já existente, conexão fechada, registro
  inexistente, listas de condições/filtros vazias e nomes de coluna desconhecidos.
- INSERT, UPDATE e DELETE com commit/rollback do chamador. Outra conexão não vê
  mudanças não confirmadas e passa a ver o INSERT depois do commit.
- Duas bases em memória com a mesma entidade permanecem independentes.
- Uma entidade sem ID aceita save e buscas por campo; operações por ID rejeitam a
  ausência de `@Id`.
- 500 INSERTs, 250 UPDATEs, 250 DELETEs e conferência de unicidade/isolamento dos
  registros. O timeout de 30 segundos detecta travamentos, não certifica desempenho.
- 40 registros gerados com semente fixa `20261008`, usados em 60 consultas AND e
  OR/AND comparadas com um resultado calculado por predicados Java. O resultado não
  é calculado pelo gerador de SQL que está sendo testado.
- `Main.main` real, com conferência dos registros exibidos em AND e OR, sem exigir
  uma ordem que a API não promete.

## Problemas reproduzidos

Os IDs abaixo correspondem aos métodos de
[KnownDefectsTest](../../src/test/java/org/com/dev/carvel/audit/KnownDefectsTest.java).
A prioridade é uma avaliação desta revisão. Herança, campos estáticos e políticas
de validação também exigem uma decisão de contrato para a v0.0.1.

| ID | Casos que falham | Prioridade | Resultado observado |
| --- | ---: | --- | --- |
| D01 | 2 | Crítica | UPDATE não escapa o apóstrofo da chave String. Uma chave normal quebra o SQL; uma chave com expressão SQL modifica outro registro. |
| D02 | 7 | Média | UPDATE aceita coluna desconhecida, em branco, duplicada e valor incompatível; ID, Row e nome nulos produzem NullPointerException em vez de validação. |
| D03 | 1 | Alta | DELETE direto aceita um nome de coluna que muda a condição e exclui dois registros. |
| D04 | 1 | Média | Entidade contendo apenas um ID gerado cria tabela, mas save falha com `Insert requires at least one row`. |
| D05 | 1 | Limitação de contrato | ID anotado na superclasse não é encontrado, porque a análise considera apenas campos declarados na classe concreta. |
| D06 | 1 | Limitação de contrato | Campo static anotado vira coluna persistida junto com os campos da instância. |
| D07 | 1 | Alta | Duas colunas de resultado com labels `id` e `ID` sobrescrevem o mesmo campo silenciosamente. |
| D08 | 1 | Média | `@GeneratedValue` sem `@Column` é ignorado sem rejeitar a declaração inválida. |
| D09 | 1 | Baixa | O executor de chave gerada lança NullPointerException para conexão nula; execute/query já usam IllegalArgumentException. |
| D10 | 6 | Média | SELECT filtrado, UPDATE e DELETE não validam metadados da tabela de maneira consistente com CREATE/INSERT. |
| D11 | 3 | Média | NaN e infinidades produzem valores literais de SQL sem validação; o contrato de rejeição antecipada desses valores não é atendido. |

### D01 — chave textual no UPDATE

Uma entidade com ID `O'Brien` é salva e consultada corretamente. Ao atualizar,
a condição do UPDATE fica:

```sql
WHERE id = 'O'Brien';
```

O H2 rejeita esse SQL. O escape da chave está em
[SqlGenerator.java](../../src/main/java/org/com/dev/carvel/sql/SqlGenerator.java#L456)
e substitui `'` por ele mesmo, em vez de duplicá-lo.

O segundo teste salva um registro com chave `x' OR '1'='1` e outro com chave
`victim`. Depois de atualizar apenas o primeiro, o label de `victim` passa de
`untouched` para `changed`. A condição gerada é:

```sql
WHERE id = 'x' OR '1'='1';
```

Esse caso comprova alteração indevida de dados através da API Repository, mesmo
quando INSERT e SELECT preservam o texto da chave corretamente.

### D03 — identificador não validado no DELETE direto

O teste cria duas linhas e passa `new Row("id = 1 OR id", 2)` ao gerador. O SQL
executado é:

```sql
DELETE FROM people WHERE id = 1 OR id = 2;
```

As duas linhas são excluídas, em vez de rejeitar o identificador. Isso foi
reproduzido na API pública SqlGenerator/SqlExecutor. `Repository.delete` obtém o
nome a partir da anotação, então a exposição dessa rota depende de quem fornece
os metadados; não foi demonstrado que um valor comum de ID altera o identificador
no Repository.

### Decisões para a versão

Antes de usar a biblioteca com entradas externas, corrigir e reexecutar D01, D03
e D07. Padronizar a validação do UPDATE e dos metadados para impedir que chamadas
inválidas só sejam descobertas pelo banco ou por NullPointerException.

Definir se a v0.0.1 suporta entidade com apenas ID gerado e campos herdados. Para
herança, campos static e valores não finitos, um escopo explícito com rejeição
clara também é uma opção; o comportamento atual não deve ficar implícito.

Esta bateria não implementa essas correções. Quando forem feitas, os testes de
contrato devem passar e sair da categoria `known-defect`, preservando a cobertura
de regressão.

## Como repetir

Com JDK 17 e Maven, na raiz do projeto:

```shell
mvn test
mvn -Pcoverage clean verify
```

`mvn test` executa os 181 casos regulares. O perfil coverage acrescenta JaCoCo e
produz `target/site/jacoco/index.html`, `jacoco.xml` e `jacoco.csv`, além do JAR.

Para executar uma classe isoladamente:

```shell
mvn -Dtest=RepositoryIntegrationTest test
mvn -Dtest=SqlQueryTest test
mvn -Dtest=SystemSmokeTest test
```

Para incluir todos os contratos de defeitos:

```shell
mvn -Pdefect-audit test
mvn -Pdefect-audit -Dtest=KnownDefectsTest test
```

**Esses dois comandos devem falhar na revisão avaliada.** O perfil não transforma
falhas em sucesso e nenhum teste usa `@Disabled`. O perfil regular exclui
explicitamente a tag `known-defect`. Portanto, um build regular verde não equivale
à aprovação da release.

Os resultados XML/TXT ficam em `target/surefire-reports` para a suíte regular e
em `target/defect-audit-reports` para a auditoria. `mvn clean` apaga esses arquivos;
execute novamente os perfis para recriá-los. Os testes individuais desta avaliação
também foram gravados em `target/individual-reports/<classe>`.

As evidências consolidadas e o inventário dos casos desta execução estão em
[v0.0.1-results.json](v0.0.1-results.json). Esse arquivo é uma fotografia desta
avaliação, não é atualizado automaticamente por Maven.

## Limites da avaliação

Foi testado H2 em memória com Java 17. Não foram testados PostgreSQL, MySQL,
SQLite, bancos em arquivo, persistência após reiniciar o processo, migrations,
falhas de rede ou grande volume em disco.

O teste com duas conexões verifica isolamento e visibilidade de transações; não
é um teste de acessos simultâneos por múltiplas threads. Não foi avaliado o uso
concorrente do mesmo Repository/Connection.

A biblioteca não promete ordenação sem ORDER BY; os testes de registros usam
conjuntos quando a ordem não faz parte do contrato. Filtros mistos respeitam a
precedência SQL (`AND` antes de `OR`); não existe agrupamento explícito por
parênteses na API atual.

Os tipos não suportados foram rejeitados nos cenários testados; não há certificação
de conversão automática de tipos, relacionamentos ou herança. A bateria de 500
registros verifica comportamento sob repetição, sem servir como benchmark.

O resultado é uma base de regressão ampla e reproduzível para este marco. As
25 falhas permanecem abertas e precisam ser consideradas na decisão de release.
